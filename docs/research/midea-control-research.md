# Midea air-conditioner control options in Go, LAN/cloud, and MCP

_Research date: 2026-09-25. This review used official documentation, upstream source, and package registries. The literature review did not itself perform device control; the local validation recorded at the end was completed separately after the survey._

## Executive recommendation

1. **For local control, use the mature community implementations as the reference layer.** [`midea-local`](https://github.com/midea-lan/midea-local) is the broadest maintained protocol library found; [`midea_ac_lan`](https://github.com/wuwentao/midea_ac_lan) is the most mature Home Assistant integration; [`msmart-ng`](https://pypi.org/project/msmart-ng/) and [`midea-ac-py`](https://github.com/mill1000/midea-ac-py) are active AC/CC-focused references. They all implement Midea's undocumented LAN protocols rather than an official Midea local API.
2. **There is no mature, general-purpose Go Wi-Fi control library in the surveyed evidence.** [`midea-porta-split`](https://github.com/thekondor/midea-porta-split) is useful only for a narrowly scoped PortaSplit V3 unit; [midea-msmart Go port](https://github.com/RelicOfTesla/midea-msmart) is an experimental translation; [legacy midea-ac library](https://github.com/bitver/midea-ac) is stale and not production-oriented. Treat a Go-native Midea adapter as code to own and test, not as a dependency to adopt blindly.
3. **For MCP in Go, use the official stable SDK, not a community Midea-specific Go server.** The [official Go SDK v1.8.0](https://pkg.go.dev/github.com/modelcontextprotocol/go-sdk) supports stdio and Streamable HTTP and includes MCP and OAuth packages. It does not implement Midea.
4. **The best MCP design reference found is [safety-first midea-mcp server](https://github.com/caroliny1031/midea-mcp), not a production-ready drop-in.** It gets several important details right—stdio, LAN-first routing, encrypted token/key storage, same-provider read-back, and no write retry after uncertain delivery—but pins `midea-local==6.11.1` and has no release or PyPI package.
5. **Operate locally.** Use stdio, or bind HTTP only to loopback. The current MCP specification requires Origin validation for Streamable HTTP, recommends loopback for local servers, and recommends authentication ([2026-07-28 transport specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)). Do not deploy a cloud-hosted Midea account proxy to the public Internet.

## Terminology: do not conflate the version numbers

- **LAN protocol V2/V3** means the Wi-Fi module/device firmware protocol spoken on the local network.
- **Midea Open Platform API v1/v2/v3** means the partner-facing cloud-to-cloud API. The current documentation exposes v3; the legacy v1 page explicitly says it is not recommended and may be withdrawn ([v1](https://mis-cdn.smartmidea.net/docs/control-midea-cloud-devices/cloud-2-cloud-api.html), [v2](https://iot.midea.com/docs/control-midea-cloud-devices/cloud-2-cloud-v2-api.html), [v3](https://iot.midea.com/docs/control-midea-cloud-devices/cloud-2-cloud-v3-api.html)).
- **MCP protocol versions** such as `2026-07-28` are a separate versioning family.

### Credential bootstrap is the fragile part

- **V2 units normally need no cloud token/key; V3 units do.** The usual V3 token is 64 bytes (128 hex characters) and the key is 32 bytes (64 hex characters). Once obtained, normal reads/writes are local ([msmart-ng documentation](https://pypi.org/project/msmart-ng/), [PortaSplit Go documentation](https://pkg.go.dev/github.com/thekondor/midea-porta-split)). `msmart-ng`'s `lan.py` separately marks the *derived per-connection* local key as valid for 12 hours; that policy is not an expiry timestamp on the stored token or key ([source](https://github.com/mill1000/midea-msmart/blob/main/msmart/lan.py)).
- The credential bootstrap used by hobby projects is **not the official Open Platform API**. It uses separate app-facing cloud routes and app credentials. Projects differ: current `midea-local` uses a Meiju `/v2/iot/secure/getToken` path, while `msmart-ng` documents NetHome Plus automation. The HA integration warns that these token services may be closed. This route can stop working independently of the LAN protocol.
- Importing a previously backed-up HA V3 credential avoids another account bootstrap, but makes that backup a high-value device secret.

## Recommended architecture and controls

1. **Bootstrap once, then prefer LAN.** Import an existing protected V3 credential if available; otherwise use a maintained bootstrap implementation only long enough to acquire token/key. Do not require cloud availability for normal operation.
2. **Keep the Midea adapter narrow.** Expose an internal interface for discovery, read, and validated state patches. If using the exact supported PortaSplit model, `midea-porta-split` is a reasonable starting point; otherwise a Python adapter based on current `midea-local` is lower risk than an unowned Go port.
3. **Use stdio by default.** If Streamable HTTP is required, bind `127.0.0.1`, retain Origin validation, and add authentication before any non-loopback exposure. Follow the official [MCP security guidance](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices).
4. **Treat token/key as credentials.** Store them in an OS keychain, secret manager, or encrypted file with restricted permissions; back up V3 credentials offline. Do not reuse the plaintext caches in `midea-local` or `smart-home-mcp` unchanged.
5. **Read before writing and constrain writes.** Seed a full state snapshot, allow only known fields, validate temperature against the device's reported limits, bind tools to configured logical device IDs, and read back through the same provider. Never automatically retry or switch provider when delivery is uncertain.
6. **Segment the Io-Fi network.** Put the AC on an IoT VLAN; allow only the controller's required discovery and device TCP flows; reserve its IP; and do not expose controller ports to guest or public networks. Broadcast discovery reveals IP, model, serial, device ID, and often MAC to the broadcast domain.
7. **Minimize cloud and log exposure.** Official partner control sends account, home, room, and device data to Midea. App-facing bootstraps send account credentials to Midea-operated services. Redact credentials and serial numbers, disable raw packet logging outside diagnostics, and pin/test dependency versions and hashes.
8. **Expect model-specific behavior.** Capability reports and undocumented commands vary by model/firmware. Energy/power decoding is not universally reliable, and raw set commands can change more fields than intended. Validate on a noncritical device and retain a physical-control recovery path.

## Bottom line

For a private LAN deployment, the evidence supports **local-first control using `midea-local` or `midea_ac_lan` as the protocol reference, with a one-time and protected V3 credential bootstrap**. For a Go/MCP service, the credible route is the **official Go MCP SDK plus an owned, narrowly scoped Midea adapter**; no existing Go Wi-Fi library has the maturity of the maintained Python/HA references. A public cloud MCP proxy is the least safe option.

## Subsequent local validation

After the survey, the three units on the user's LAN were discovered and their SmartHome cloud inventory was mapped. All three speak LAN protocol V3 and authenticated successfully with separately obtained per-device token/key pairs:

| Cloud name | IP | Model | LAN protocol | Stored credential verified |
|---|---|---|---|---|
| living-room | `192.0.2.153` | `00000Q1F` | V3 | yes |
| bedroom | `192.0.2.131` | `00000Q18` | V3 | yes |
| kids-room | `192.0.2.130` | `00000Q18` | V3 | yes |

The bedroom unit was powered on and read back through an independent implementation, then powered off on request and read back again. The account password was not retained; the device token/key pairs are stored only in a mode-`0600` user configuration file. The token bootstrap response exposed no expiry field. That supports treating the pairs as long-lived device credentials, but not promising that re-pairing, factory reset, module replacement, or cloud-side revocation can never invalidate them.

Measured during the Go port: the cloud returns a **different token and key on every `getToken` call** (three consecutive fetches minutes apart produced three distinct pairs per unit), yet a previously issued pair **still authenticated all three units** after a newer pair had been fetched and stored. The working model is therefore "the cloud mints a fresh pair per request and the device accepts the pairs it has been issued", not "one stable secret". Re-bootstrapping is therefore safe for other consumers holding an older pair, but it does rewrite the stored value.

The implemented Go service deviates from recommendation 2 above: it uses the pinned `midea-porta-split` V3 client for the LAN protocol, and a native Go port of the SmartHome handshake for the credential bootstrap, rather than a Python runtime adapter. Both were exercised against these three specific units. The cloud port is pinned to the same handshake constants the maintained Python clients use and is covered by vectors captured from that reference implementation, but the vendor endpoints are undocumented and can change without notice. The protocol dependency is isolated behind a small internal interface so it can be swapped without changing the CLI or MCP surface.

Two protocol details were settled empirically rather than trusted:

- **The mode and fan tables are not in dispute for these units.** `msmart-ng` and `midea-porta-split` publish byte-for-byte identical tables (AUTO=1, COOL=2, DRY=3, HEAT=4, FAN_ONLY=5, plus SMART_DRY=6 in msmart only; fan AUTO=102, SILENT=20, LOW=40, MEDIUM=60, HIGH=80, FULL=100), and both read the same live values from all three units. The upstream README's warning about disagreeing mode values refers to `midea_ac_lan`, a third implementation, not to msmart-ng.
- **The writable surface depends on whether the unit is running.** With a unit powered off, only `power`, `mode`, `fan speed` and `target temperature` took effect; `eco`, `turbo`, `sleep`, `display` and both swing flags were accepted on the wire and then ignored. Repeating the test on a powered-on unit (living-room) changed the picture: both swing directions worked, `sleep` was accepted once and then cleared by the unit, while `eco`, `turbo` and `display` remained refused. A one-shot probe of a powered-off unit is therefore not sufficient to determine a device's writable surface. The unsupported flags stay exposed and report a read-back disagreement rather than a false success.

The units also report no temperature limits in their capability response (all-zero), so temperature validation falls back to a conservative 17–30 °C range in 0.5 °C steps. The outdoor-temperature field was not stable across a single session (25 °C, then 19 °C on the same unit with no relevant change), so outdoor readings should be treated as indicative only.
